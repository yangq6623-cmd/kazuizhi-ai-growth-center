# V1.9.5 与 V1.8.5 功能回归对比记录

日期：2026-09-15

## 结论

当前 V1.9.5 Enterprise R3 已解决 Windows 构建、安装、旧 Dashboard、旧端口与前端资源混用问题，但它还不是 V1.8.5 的完整功能超集。

用户通过 V1.8.5 与 V1.9.5 界面截图对比确认：V1.9.5 当前存在明显功能缺失 / 功能未迁移 / 仅保留界面占位的情况。

这属于功能回归，后续升级必须优先修复。

## 为什么会出现

本轮 V1.9.5 的主要开发重心曾经转向：
- 重新建立可维护源码结构；
- 修复 GitHub Actions；
- 修复 PyInstaller 前端打包；
- 修复 Inno Setup；
- 清理旧构建污染；
- 隔离旧 8765 端口与旧进程；
- 让新版 Dashboard 能稳定安装、启动和显示。

因此 R2/R3 阶段先建立了一个新的 Enterprise Dashboard / 运营驾驶舱基线，但没有完成 V1.8.5 全部已验证功能的一比一迁移。

换句话说：当前 R3 是“稳定的新运行壳 + 新驾驶舱 + 部分模块入口”，不是“V1.8.5 全功能 + V1.9.5 新功能”的最终升级版。

## 与项目既定原则冲突

仓库 `docs/BASELINE_ASSETS_INDEX.md` 已明确规定 V1.9.5 重构原则：

1. 保留 V1.8.x 已验证能力；
2. 不丢失历史数据、学习记录、审计记录；
3. 补齐可维护源码结构；
4. 新版本必须包含升级说明、测试记录、回滚方案。

因此后续不能把当前 R3 的“可安装、可启动”误认为整个 V1.9.5 已完成功能升级。

## 从当前截图能确认的问题

### V1.8.5

旧版界面包含更多已经形成产品形态的功能区、信息区和操作入口，整体更接近“完整运营系统”。

### V1.9.5 R3

当前新版界面虽然视觉和结构更现代，但仍存在：
- 多项 KPI 显示 `--`；
- 多处显示“准备接入 / 待接入 / 待统计 / 待执行”；
- 部分菜单只是入口或占位，没有完整业务页；
- AI、自动化、SEO/GEO、业务数据等多处尚未恢复到 V1.8.5 已有能力；
- 左侧还存在重复菜单 / 重复分组等 UI 收尾问题。

## 正确修复方向

不能退回 V1.8.5，也不能继续只完善 R3 外壳。

应采用：

`V1.8.5 全能力盘点 → 与 R3 做差异矩阵 → 在 R3 稳定构建基线上逐项恢复 → 每项回归测试 → 最终 V1.9.5 必须成为 V1.8.5 的功能超集`

### P0：先冻结当前 R3 构建基线

不得破坏：
- R3 端口 8876；
- 独立 AppId / 安装目录；
- PyInstaller 前后双 Marker 校验；
- 当前可成功安装启动的 Workflow。

### P1：建立 V1.8.5 功能清单

来源：
- V1.8.5 Windows 发布包；
- V1.8.5 交接文档；
- V1.8.4 / V1.8.3 / V1.8.2 历史交接文档；
- 用户提供的 V1.8.5 运行截图；
- 历史数据 / 学习 / 审计 / 自动化记录。

对每个功能标记：
- A：R3 已完整存在；
- B：R3 有入口但未实现；
- C：R3 完全缺失；
- D：功能存在但真实数据未接；
- E：需要升级重构。

### P2：优先恢复功能而不是继续加新外观

优先级：
1. V1.8.5 已经可用、现在缺失的核心功能；
2. 历史数据 / 学习 / 复盘 / 审计类能力；
3. 业务数据、订单、用户、师傅、团长真实接口；
4. SEO/GEO、AI 任务、自动化调度完整执行链；
5. 新增 V1.9.5 能力。

### P3：建立回归测试清单

V1.9.5 正式发布前必须逐项确认：
- V1.8.5 已验证功能没有减少；
- 数据没有丢；
- 历史记录可读；
- 原有自动化能力可用；
- 新 Dashboard 不只是展示壳；
- 新功能在旧能力基础上增加，而不是替代并丢失旧功能。

## 当前状态定义

当前应定义为：

**V1.9.5.3 Enterprise R3：构建/安装/启动/新版 Dashboard 基线稳定，但功能迁移尚未完成，存在相对 V1.8.5 的功能回归。**

后续不得把“R3 能安装打开”直接标记为“V1.9.5 完成”。
