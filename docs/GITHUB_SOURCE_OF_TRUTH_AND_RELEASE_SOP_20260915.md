# GitHub 单一事实源与发布交付 SOP

日期：2026-09-15

## 1. 目标

以后所有卡嘴子 AI 增长运营中心的正式源码、构建脚本、版本说明、交接文档、测试记录和稳定基线，都以本 GitHub 仓库为第一事实源（Source of Truth）。

目标：避免再次出现“安装包能找到，但源码找不到”“旧功能做过但不知道在哪”“聊天里说过但 GitHub 没记录”“重新升级时误用旧前端/旧端口/旧构建目录”等问题。

## 2. 用户侧交付方式

以后默认采用：

1. 在 GitHub 中维护源码与文档；
2. 通过 GitHub Actions 构建 Windows EXE / Setup；
3. AI 侧直接检查最新成功 Run 和 Artifact；
4. AI 侧把最终测试包直接交付给用户下载；
5. 用户只负责在本机运行安装包并做最终视觉/功能验收；
6. 用户不需要每次自己进入 GitHub 寻找 Artifact。

GitHub 是长期保存与恢复入口，不要求老板日常手动管理。

## 3. 每个正式版本必须在 GitHub 保留的 8 类资产

1. **完整源码**：运行核心、前端、数据结构、AI/增长逻辑。
2. **构建源码**：PyInstaller spec、PowerShell 构建脚本、Inno Setup 脚本。
3. **CI 构建流程**：`.github/workflows/`。
4. **版本状态**：`VERSION`、`CHANGELOG.md`、`*_BUILD_STATUS.md`。
5. **总交接文档**：为什么改、改了什么、没动什么、已知问题、下一步、回滚点。
6. **功能回归清单**：上一稳定版本 → 当前版本，确保旧能力不丢。
7. **稳定回退点**：baseline 分支或 tag + 成功 commit + 成功 Run ID。
8. **发布产物定位信息**：Artifact 名、ID、安装包名、SHA256（如有）。

## 4. 禁止事项

- 禁止只把 EXE/ZIP 当作唯一备份而不保存源码。
- 禁止只在聊天里记录功能和产品理念。
- 禁止新版本重构后把已接入功能变成“待接入”却不记录。
- 禁止用旧完整文件直接覆盖当前 main。
- 禁止修改正式端口、AppId、前端来源、构建路径后不更新交接文档和回归测试。
- 禁止删除历史稳定分支/交接索引，除非已有等价可恢复基线。

## 6. 当前发现的历史归档缺口

当前 GitHub 已有 V1.8.x 的交接索引和历史说明，但 `01_Legacy_V1.0-V1.8.5/` 目前并未完整保存 V1.8.5 的全部历史源码/Windows 发布包。

这意味着：
- V1.9.5 R3 当前源码可继续维护；
- 但如果未来需要逐字节还原 V1.8.5 的原始程序，仅靠当前 GitHub 仍不够；
- 因此应继续把可找回的 V1.8.5 交接文档、发布包、升级器、源码/核心文件、SHA256 等补入历史归档。

在补齐前，V1.8.5 功能恢复以：历史交接文档 + File Library + 已确认截图 + 本地备份/Google Drive 对接中心为依据。

## 7. 后续每次发布固定流程

`开发分支/增量修改 → 本地/结构校验 → GitHub Actions → 安装包生成 → 自动/人工内测 → 实机安装验收 → 更新交接文档 → 创建稳定 baseline/tag → 交付用户最终 Setup`

每一步都必须可追踪。

## 8. 用户以后需要怎么做

默认不需要老板自己在 GitHub 找安装包。

AI 侧负责：
- 找最新源码；
- 修改；
- 构建；
- 查 Run；
- 查 Artifact；
- 下载最终测试包；
- 直接把安装包链接/文件交给老板。

老板侧只需要：
- 下载；
- 安装；
- 打开；
- 把最终验收截图/功能结果发回。

## 9. 发生异常时的恢复顺序

1. 先看 `docs/AI自动化交接文档_INDEX.md`；
2. 读最新总交接/产品方向；
3. 看 `VERSION / BUILD_STATUS / CHANGELOG`；
4. 对比最新稳定 baseline 分支；
5. 查成功 GitHub Actions Run 和 Artifact；
6. 查历史版本交接和功能回归清单；
7. 必要时回滚到最后一次已实机验证成功的稳定基线。

## 10. 最终原则

**GitHub 保存“怎么做出来”，Artifact 保存“做出来的包”，交接文档保存“为什么这么做”。三者缺一不可。**
